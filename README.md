# 14 周大模型应用开发 · 学习工作台

把「12 周学习计划」（另加 2 周缓冲）落成可以每天打卡、记笔记、记疑点的东西。

## 目录结构

```
learning-workbench/
├── README.md                本文件
├── resources.yaml           文档库（56 条，官方文档/仓库为主）
├── videos.yaml              视频库（39 条，每条核验 bvid、UP 主、时长、播放量）
├── weeks/
│   ├── w01.yaml ... w14.yaml   每周 7 天，共 98 天
└── build.py                 编译脚本：YAML → 可读计划 + 可打卡表格
    dist/
    ├── plan.md              可阅读的完整计划（含可点击链接）
    ├── plan.csv             平面数据，可导入飞书/Notion/Excel
    ├── plan.json            结构化数据，给将来的网站/小程序用
    └── 学习工作台.xlsx       带打卡、疑点、复盘、统计的工作簿
```

**设计原则：计划是数据，视图是生成物。** 想改计划就改 `weeks/*.yaml`，然后重新生成；
不要手改 `dist/` 里的文件，否则下次生成会被覆盖。

## 快速开始

```bash
# 重新生成全部产物（需要能 import openpyxl 的 Python）
python3 build.py
```

- **只想看计划**：打开 `dist/plan.md`
- **想开始打卡**：打开 `dist/学习工作台.xlsx` → 「总览」B2 填开学日期
- **想搬到飞书/Notion**：导入 `dist/plan.csv`

## 每天怎么用（3 步，5 分钟）

1. 打开「每日计划」，按 `日期` 列找到今天那一行。
2. 做「任务」，做完把 `状态` 改成 **已完成**（下拉选项）；没做完改 **顺延**。
3. 卡住的地方立刻写进「疑点清单」，别留在脑子里。

> **完成标准**：① 有产出物（代码/提交/文档）② 有一条能讲给别人听的笔记 ③ 有一个明确疑点。
> 「看完视频」不算完成，这三个都齐了才算。

## 疑点怎么复习

「疑点清单」里有两个状态动作：

- 状态：`未解决 → 查资料中 → 已搞懂 → 放弃`
- 搞懂后填「下次复习」，按 **1 / 3 / 7 / 15 天** 递增，写进「复习次数」：

| 复习次数 | 间隔 |
|---|---|
| 1 | +1 天 |
| 2 | +3 天 |
| 3 | +7 天 |
| 4+ | +15 天 |

只看「下次复习 ≤ 今天」的行，5 分钟能过完。

## 每周怎么收口

每周第 7 天固定是 **复盘 + 缓冲**，已被写进计划里，不是额外负担：

1. 把「顺延」的任务补掉，或明确放弃（放弃也要写下来）。
2. 填「周复盘」：完成了什么 / 卡在哪一步 / 下周砍掉什么。
3. 「总览」会显示完成率和是否落后——落后就把缓冲日用来补，不要往后拖整周。

## 视频库的可信度

`videos.yaml` 里 39 条视频，每条都通过 B 站接口核验过 `bvid / 标题 / UP 主 / 时长 / 播放量`
（核验日期 2026-11-09）。工作簿「资源库」有对应列，可以按播放量或发布年份筛选。

两点提醒：

- 播放量是核验当天的快照，会变；
- 长课程（>3 小时）标注了「只看哪部分」，**不要顺序刷**，否则第 3 周就会卡住。

## 换资源 / 加资源

1. 打开 `videos.yaml` 或 `resources.yaml`，复制一条改字段；
2. 在 `weeks/wNN.yaml` 的 `refs` 里加上新 id（放在最前面 = 当天主推）；
3. 跑 `python3 build.py`，校验会告诉你 id 是否写错。

```yaml
# weeks/w03.yaml 片段
  - id: W03D05
    day: 5
    title: PGVector 上手
    minutes: 160          # 预估时长，会影响总览的统计
    goal: 用自己的库存向量，能查、能过滤。      # 一句话，别写长
    tasks:                # 3-4 条，每条都是可执行动作
      - docker 起 pgvector，建带 vector 列的表
    deliverable: 可查询的向量表 + 建表 SQL     # 产出物，验收用
    refs: [r-pgvector, r-pgvector-docker, v-pgvector]   # 引用资源库 id
    notes_prompt: 索引参数（m、ef_construction）影响什么？
```

改完跑一次 `python3 build.py`，脚本会校验：

- 是否 14 个文件、每周 7 天、id 是否 `W{周}D{天}`
- `refs` 是否都存在于 `resources.yaml`
- 每周预估时长是否超过 20 小时（防止把计划排成不可能完成的量）

## 资源为什么是这种形式

| 类型 | 做法 | 原因 |
|---|---|---|
| 官方文档 | 直接给稳定 URL | 能查证、不会过期、面试前还能回看 |
| 视频 | 给**平台搜索页** + 筛选标准（如「选近一年、播放量高、有配套代码」） | 具体视频半年内大概率失效；给检索入口反而长期可用 |
| 每个资源 | 必填「看完应能回答」 | 防止「看完 = 学会」的错觉 |

链接失效时只改 `resources.yaml` 一处，再重新生成，计划里引用它的天会自动更新。

## 时间预算

| 阶段 | 周次 | 主题 | 预估 |
|---|---|---|---|
| A | 1-2 | Java 工程 + LLM 最小闭环 | 30 h |
| B | 3-5 | RAG（含评测） | 46 h |
| C | 6-8 | Agent（含生产化底座） | 46 h |
| D | 9-10 | 可观测性与安全 | 30 h |
| E | 11-12 | MCP 与作品打磨 | 32 h |
| F | 13-14 | 缓冲补课 + 拓展求职 | 33 h |
| | | **合计** | **≈ 218 h（日均 2.2 h）** |

如果每天只能投入 1 小时，把周期按 1.5 倍拉长即可（21 周），**不要压缩每天的深度**。
进度落后时优先用每周第 7 天的缓冲日，而不是熬夜补齐。
